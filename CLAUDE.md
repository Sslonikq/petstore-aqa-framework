# petstore-api-automation

Production-like фреймворк для API-автотестов на базе Swagger Petstore OpenAPI (`https://petstore3.swagger.io/api/v3`). Пет-проект, цель которого — показать, что автор умеет самостоятельно спроектировать, собрать и поддерживать AQA-фреймворк, а не просто писать отдельные API-тесты. OpenAPI-контракт — источник истины по эндпоинтам, payload'ам и статус-кодам.

## Как это работает (слои)

```
тест
  → PetApi / StoreApi / UserApi   (знает эндпоинты, бизнес-вызовы)
  → BaseApiClient                  (знает транспорт: httpx, заголовки, auth, ретраи, таймаут, логирование)
  → httpx.Client / AsyncClient
  → Swagger Petstore API
```

Вокруг этого пайплайна: фикстуры, фабрики данных на Faker, Pydantic-модели, хелперы-ассерты, Allure-репортинг — всё подключается через `conftest.py`, но транспортом никто из них не владеет.

Тест должен выглядеть так:

```python
response = pet_api.create_pet(pet)
assert response.status_code == 200
created = PetResponse.model_validate(response.json())
assert created.id == pet.id
```

Никаких сырых вызовов `httpx`/`requests` внутри теста — для этого есть `BaseApiClient`.

## Ключевые архитектурные решения (важно не сломать)

- **Слой API Object, а не терминология Page Object.** `PetApi`/`StoreApi`/`UserApi` — это API-аналог Page Object. Они знают эндпоинты; `BaseApiClient` знает транспорт; тесты знают бизнес-ассерты. Не дублировать пути эндпоинтов/заголовки/auth по тестам — всё через слой клиента.
- **Клиент выполняет, тесты проверяют.** В `BaseApiClient` не должно быть ассертов — только выполнение запроса, ретраи, логирование, auth, таймауты.
- **Sync по умолчанию, async — только когда оправдан.** Большинство CRUD-операций — простой запрос/ответ без выгоды от конкурентности. `httpx.AsyncClient` используется только там, где реально нужна параллельность (параллельные запросы). Не делать весь сьют асинхронным ради демонстрации `async/await`.
- **Две разные проверки — не путать.** Pydantic валидирует *свои* модели запроса/ответа (типы, обязательные поля, enum'ы). Валидация OpenAPI-контракта проверяет *совместимость с контрактом*. Формулировка «Pydantic валидирует OpenAPI-спеку» — ошибка категории, это разные слои и разные инструменты.
- **Конфигурация полностью через окружение.** Никаких захардкоженных URL/ключей/секретов в коде — `.env` + типизированный объект настроек. `.env` никогда не коммитится; `.env.example` содержит безопасные значения и коммитится.
- **Тестовые данные — через фабрики, не инлайн-рандом.** `PetFactory`/`UserFactory`/`OrderFactory` оборачивают Faker, дают валидные значения по умолчанию с возможностью переопределения (`PetFactory.build(name=...)`). Если случайные данные приводят к падению теста, сгенерированный инпут должен быть виден в логах/Allure, чтобы падение можно было воспроизвести.
- **Ретраи — узкие и честные.** Только транзиентные/сетевые сбои, никогда — падения ассертов, никогда не используются, чтобы скрыть нестабильные тесты. Количество и таймаут — конфигурируемые.
- **Тесты независимы; чейнинг — по желанию.** Ни один тест не должен зависеть от порядка выполнения других. Цепочки сценариев (create → get → update → delete → get-404) нужны для реалистичного интеграционного покрытия, но не должны становиться хребтом всего сьюта.
- **Никогда не считать поведение «типичным REST»-поведением по умолчанию.** Важны только актуальный OpenAPI-контракт и реально наблюдаемое поведение. Если реальное поведение Petstore расходится с документацией — фиксировать расхождение, а не тихо закладывать его как обязательное требование.

## Структура

```
config/            типизированные настройки из .env — ничего внутреннего не импортирует, лист графа зависимостей
api/
  base_client.py    BaseApiClient — транспорт: httpx, auth, заголовки, таймаут, ретраи, логирование
  async_client.py   асинхронный транспорт, используется только там, где нужна конкурентность
  async_pet_api.py  асинхронный API-объект; зеркалит не весь PetApi, а только операции, которым нужен gather
  pet_api.py / store_api.py / user_api.py   знание эндпоинтов по ресурсу
models/            Pydantic-модели запроса/ответа (Pet, User, Order, Category, Tag)
factories/         билдеры данных на Faker (PetFactory, UserFactory, OrderFactory)
assertions/        общие/кастомные хелперы для ассертов
tests/
  api/{pet,store,user}/   CRUD + позитивные/негативные/граничные по ресурсу
  contract/               тесты совместимости с OpenAPI-контрактом
  integration/            цепочечные/end-to-end сценарии
utils/logging.py    логирование запросов/ответов, секреты маскируются
conftest.py         фикстуры: api_client, pet_api/store_api/user_api, фабрики, created_pet (с очисткой)
.github/workflows/tests.yml   CI: checkout → setup Python → install → lint/type-check → pytest → публикация Allure/артефактов
Dockerfile / docker-compose.yml   воспроизводимый запуск тестов (сам Petstore остаётся внешним, не контейнеризуется)
```

Это целевая структура, а не чек-лист — файл создаётся только тогда, когда функциональность за ним реально появляется.

## Запуск

```bash
pytest
pytest -m smoke
pytest -m regression
pytest -m contract
pytest -m concurrent
```

Команды для Docker/Allure/линта/CI документируются в `README.md` по мере реализации.

`.env` (никогда не коммитится — см. `.env.example`):

```
BASE_URL=https://petstore3.swagger.io/api/v3
API_KEY=
TIMEOUT=10
RETRY_COUNT=2
```

## Конвенции

- `config` ничего внутреннего не импортирует — остаётся листом графа зависимостей, чтобы не было циклов.
- Секреты/креды — только в файлах из `.gitignore`, никогда в коде или коммитах.
- Маркеры используются осмысленно: `smoke, regression, positive, negative, contract, concurrent, slow` — не добавлять маркер без причины. `async` как имя маркера невозможно: это зарезервированное слово Python, `@pytest.mark.async` не разбирается.
- Форматтер/линтер/тайпчекер (ruff/mypy) добавляются только тогда, когда у них есть конкретная роль, а не для галочки.

## Процесс добавления фичи

1. Определить поведение и решить, какой слой за него отвечает (клиент / API-объект / модель / тест).
2. Реализовать минимально достаточную абстракцию — без попутных рефакторингов.
3. Добавить/обновить тесты (позитив + негатив там, где уместно); прогнать их, затем весь сьют.
4. Прогнать линт/тайпчек, если настроены; обновить документацию, если поведение изменилось.
5. Коммитить только после зелёного прогона.

## Текущий статус / не-цели

Репозиторий собирается с нуля, примерные стадии: фундамент → модели и данные → покрытие тестами → контрактное тестирование → инженерное качество (логирование/ретраи) → репортинг и CI → async → hardening. Не считать, что запланированный файл уже существует, пока он реально не реализован.

Явно вне скоупа: Selenium/Playwright/UI-автоматизация, Page Object для веб-страниц, LLM/AI-слой, произвольные сторонние сервисы не по теме, интеграция с БД (пока не появится конкретная обоснованная потребность — тогда это будет отдельный проект).
