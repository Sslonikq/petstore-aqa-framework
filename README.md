# petstore-aqa-framework

[![CI](https://github.com/Sslonikq/petstore-aqa-framework/actions/workflows/tests.yml/badge.svg)](https://github.com/Sslonikq/petstore-aqa-framework/actions/workflows/tests.yml)
[![Allure Report](https://img.shields.io/badge/Allure-report-brightgreen)](https://sslonikq.github.io/petstore-aqa-framework/)
[![Python](https://img.shields.io/badge/python-3.11%2B-blue)](https://www.python.org/)

Фреймворк API-автотестов для [Swagger Petstore](https://petstore.swagger.io/). Проект показывает не набор тестов, а спроектированный фреймворк: слои с разделённой ответственностью, конфигурация через окружение, контрактное тестирование, репортинг, CI и воспроизводимый запуск в контейнере.

Источник истины по эндпоинтам, схемам и статус-кодам - OpenAPI-контракт, а не догадки о том, как «обычно работает REST».

**45 тестов**: 19 позитивных, 7 негативных, 17 контрактных, 2 конкурентных, 2 цепочечных.

| Отчёты | Allure |

| Запуск | Docker, docker compose |

## Архитектура

```
тест                       бизнес-ассерты
  ↓
PetApi / StoreApi / UserApi        знает эндпоинты
  ↓
BaseApiClient                      знает транспорт: httpx, заголовки, таймаут, ретраи, логирование, вложения Allure
  ↓
httpx.Client / httpx.AsyncClient
  ↓
Swagger Petstore API
```

Тест выглядит так и никак иначе:

```python
response = pet_api.create_pet(pet)

assert response.status_code == 200
created = Pet.model_validate(response.json())
assert created.id == pet.id
```

### Решения, на которых стоит фреймворк

**Слой API Object.** `PetApi`/`StoreApi`/`UserApi` знают пути и параметры; `BaseApiClient` знает транспорт; тесты знают только бизнес-проверки. Сырых вызовов `httpx` в тестах нет ни одного - это не стилистика, а условие герметичности: всё, что добавлено в транспорт (логи, ретраи, вложения в отчёт), автоматически распространяется на каждый тест, включая ненаписанные.

**Композиция вместо наследования.** API-объекты держат клиент в поле, а не наследуются от него. Асинхронный клиент - отдельный класс, а не наследник синхронного: `await` нельзя надстроить над блокирующим вызовом, асинхронность должна быть в самом низу.

**Клиент выполняет, тесты проверяют.** В `BaseApiClient` нет ни одного ассерта - только запрос, ретраи, логирование, заголовки, таймаут.

**Единая воронка `_request`.** Каждый запрос проходит через один метод, поэтому логирование, маскировка секретов, вложения Allure и ретраи написаны один раз.

**Конфигурация только через окружение.** Ни одного захардкоженного URL или ключа. `.env` не коммитится, `.env.example` коммитится. Переключение стенда - одна переменная, и это уже проверено тремя способами: `.env` локально, `environment` в docker-compose, `env` в CI.

**Ретраи узкие и честные.** Повторяется только транзиентный сетевой сбой (`httpx.TransportError`). Ответ 500 не повторяется никогда: это корректный HTTP-ответ, и молчаливый повтор прятал бы поломку сервера.

**Данные через фабрики.** `PetFactory`/`OrderFactory`/`UserFactory` оборачивают Faker и дают валидные значения с возможностью переопределить: `PetFactory.build(name="")`. Сгенерированный вход виден в логах и во вложениях Allure, поэтому падение на случайных данных воспроизводимо.

**Тесты независимы.** Каждый создаёт то, что ему нужно, и убирает за собой фикстурой. Порядок выполнения ни на что не влияет, подготовленные заранее данные на стенде не требуются.

## Запуск

### Локально

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux, macOS

pip install -e .
cp .env.example .env

pytest
```

### Переменные окружения

`.env` не коммитится, безопасный образец лежит в `.env.example`:

```
BASE_URL=https://petstore.swagger.io/v2
API_KEY=
TIMEOUT=10
RETRY_COUNT=2
```

Переменная окружения приоритетнее `.env`, поэтому стенд переключается без правки файлов:

```bash
BASE_URL=https://petstore3.swagger.io/api/v3 pytest
```

### Маркеры

```bash
pytest                     # все 45
pytest -m smoke            # 3 критических сценария
pytest -m contract         # 17 контрактных
pytest -m negative         # 7 негативных
pytest -m concurrent       # 2 на конкурентность
pytest -m "not slow"       # 41, без длинных сценариев
```

Маркеры: `smoke`, `positive`, `negative`, `contract`, `concurrent`, `slow`. Маркер, не проставленный ни одному тесту, удаляется - `--strict-markers` включён.

Имя `async` для маркера невозможно: это зарезервированное слово Python, `@pytest.mark.async` не разбирается интерпретатором.

## Docker

Воспроизводимый прогон без установки Python и зависимостей:

```bash
docker compose run --rm tests                     # все тесты
docker compose run --rm tests pytest -m smoke     # выборочно
docker compose build                              # пересобрать образ
```

Образ 275 МБ на базе `python:3.11-slim`, сборка с нуля около 40 секунд. `allure-results` пробрасываются томом на хост, поэтому отчёт собирается снаружи контейнера.

Сам Petstore не контейнеризуется: это внешний публичный сервис, а не часть тестируемой системы.

Порядок `COPY` в Dockerfile выбран под кеш слоёв: зависимости и код фреймворка копируются до `pip install`, тесты - после. Правка теста пересобирает один слой, а не тянет пакеты заново.

**Если из контейнера приходит 403**, доступ к Petstore блокируется по региону и нужен прокси. Добавить в `docker-compose.yml`:

```yaml
environment:
  ALL_PROXY: socks5://host.docker.internal:10808
```

`host.docker.internal` - имя, которое Docker Desktop резолвит в адрес хоста; `127.0.0.1` указал бы контейнер сам на себя.

## Allure

```bash
pytest
allure serve allure-results
```

Или с сохранением отчёта в проект:

```bash
allure generate allure-results -o allure-report --clean
allure open allure-report
```

Требуется Allure CLI и Java. Обе команды запускаются из корня проекта: пути относительные.

Что попадает в отчёт:

- **Тело запроса и ответа на каждый HTTP-вызов.** Прикрепляются в `BaseApiClient._request`, то есть автоматически для всех тестов, включая запросы из фикстур - они ложатся в секции Set up и Tear down. Упавший тест в CI разбирается по отчёту, без воспроизведения локально.
- **Параметры стенда** в блоке Environment: `BASE_URL`, `TIMEOUT`, `RETRY_COUNT`, `API_KEY_SET`. Значение ключа не пишется никогда, только факт его наличия.
- **Группировка по эпикам и фичам** во вкладке Behaviors: Pet, Store, User, Контракт, Интеграция.
- **Шаги внутри цепочечных тестов** - видно, на каком именно шаге сценарий сломался.

Секреты маскируются перед записью в лог и во вложение одной функцией, поэтому два канала не могут разойтись.

## CI

[`.github/workflows/tests.yml`](.github/workflows/tests.yml) на push и pull request в `main`, плюс ручной запуск.

Шаги: checkout → Python 3.11 с кешем pip → `pip install -e .` → `pytest` → выгрузка `allure-results` артефактом → сборка отчёта → публикация на GitHub Pages.

Все шаги отчёта помечены `if: always()`, поэтому отчёт публикуется и при красном прогоне - именно тогда он и нужен. Деплой дополнительно ограничен веткой `main`, чтобы прогон на pull request не перезаписывал опубликованный отчёт.

История прогонов копируется из ветки `gh-pages` перед сборкой, за счёт этого в отчёте работает график Trend.

Отчёт последнего прогона: **https://sslonikq.github.io/petstore-aqa-framework/**

## Контрактное тестирование

Три разных проверки, которые легко спутать:

**Схемы ответов** (`test_response_schemas.py`) - ответ сервера валидируется через `jsonschema` против схемы, скачанной из живого `swagger.json`. Проверяется совместимость с контрактом.

**Синхронизация моделей** (`test_model_sync.py`) - набор полей, набор обязательных полей и значения enum в наших pydantic-моделях сверяются со спецификацией. Если контракт изменится, тест покажет расхождение раньше, чем оно проявится в продуктовых тестах.

**Известные расхождения** (`test_known_deviations.py`) - тесты, которые проверяют поведение **по документации** и помечены `xfail(strict=True)`. Строгий режим важен: если Petstore однажды починят, тест перейдёт в `XPASS` и упадёт, сообщив, что расхождение исчезло и запись пора удалить.

Отдельно стоит различать pydantic и валидацию контракта: pydantic проверяет наши модели запроса и ответа (типы, обязательные поля, enum), валидация контракта проверяет совместимость со спецификацией. Это разные слои и разные инструменты.

## Расхождения Petstore с документацией

Найдены при разработке тестов и зафиксированы в коде, а не в голове.

### Зафиксированы xfail-тестами

| # | Эндпоинт | Контракт | Реальность |
|---|---|---|---|
| 1 | `GET /pet/findByStatus` | 400 `Invalid status value` на значение вне enum | 200 и пустой список на любое значение |
| 2 | `GET /pet/findByStatus` | параметр `status` объявлен required | без него 200 и пустой список |
| 3 | `GET /store/order/{orderId}` | у `orderId` объявлен `maximum: 10` | заказ с бо́льшим id читается с кодом 200 |
| 4 | `DELETE /store/order/{orderId}` | описаны только 400 и 404 | успешное удаление возвращает недокументированный 200 |
| 5 | `GET /user/login` | 400 `Invalid username/password supplied` | сессия выдаётся на любой пароль, аутентификации фактически нет |

### Наблюдения, не противоречащие контракту

**6. Пустое и сверхдлинное имя питомца принимаются.** `name` объявлен обязательным, но `minLength` и `maxLength` в схеме `Pet` не заданы. Значит `required` означает «поле передано», а не «значение осмысленно». Имя из 10000 символов сохраняется целиком, без обрезки. Формально сервер прав, и тесты зафиксированы как наблюдение, а не как баг.

**7. Данные на стенде нарушают собственную схему.** `findByStatus` возвращает питомцев без обязательного поля `name`; `/store/inventory` содержит ключи вне enum, включая `INVALID_STATUS` и `'sold '` с пробелом на конце. Стенд публичный и общий, данные туда пишет кто угодно. Поэтому проверки построены на инвариантах («все питомцы в выдаче имеют запрошенный статус»), а не на количествах и составе выдачи.

**8. `PUT /user/{username}` возвращает `ApiResponse`, а не `User`.** Ловушка при написании тестов: у модели `User` нет обязательных полей, поэтому `User.model_validate` на чужом теле не падает, а молча возвращает объект со всеми `None`. Ассерт затем сравнивает `None` с ожидаемым значением, и причина падения выглядит совершенно не там, где она есть.

**9. Сервер периодически отдаёт 500 на запись.** На `petstore3.swagger.io/api/v3` это было воспроизводимо постоянно (10 из 10 попыток `POST /pet`), из-за чего `BASE_URL` переключён на `v2`. На `v2` пятисотки эпизодические. Ретраями это не закрывается сознательно: 500 - корректный HTTP-ответ, а не сетевой сбой, и повтор прятал бы поломку сервера.

## Асинхронный слой

`httpx.AsyncClient` используется только там, где конкурентность даёт реальный выигрыш. Остальной сьют синхронный, и это осознанно: `await` заразен и распространяется по всей цепочке вызовов, поэтому «сделать всё асинхронным» - решение про весь фреймворк, а не про один тест. Для CRUD-запроса «отправил, дождался, проверил» выгоды нет никакой.

Замер на десяти созданиях питомца, три прогона:

| последовательно | через `asyncio.gather` | ускорение |
|---|---|---|
| 2.54s | 0.88s | 2.9x |
| 2.37s | 1.24s | 1.9x |
| 2.32s | 1.20s | 1.9x |

Ускорение около двукратного, а не десятикратного по числу запросов: узкими местами становятся сеть и общий публичный сервер, который не обязан обрабатывать запросы параллельно.

Проверки времени в тестах намеренно нет: разброс конкурентного замера (0.88s против 1.24s) сделал бы такой ассерт мигающим, а мигающий тест хуже отсутствующего.

Асинхронный слой дал и то, чего без него не существовало бы: `test_read_same_pet_concurrently` бьёт десятью одновременными запросами в один объект и проверяет, что сервер не путает ответы и не отдаёт частичные данные.

## Что сознательно не сделано

**Модульных тестов нет.** Код фреймворка - тонкая прослойка над httpx, вся его работа в сетевом вызове. Изолировать сеть моками, чтобы проверить «`post` вызывает `_request` с методом POST», значит написать тавтологию: тест повторит реализацию и сломается при любом рефакторинге, не поймав ни одного бага. Кандидаты с настоящей логикой есть - `mask_secrets` и `to_payload`, - и если категорию закрывать, то ими.

**Папки `assertions/` нет.** Общие хелперы для ассертов не понадобились: проверки простые и локальные. Заводить модуль ради строчки в схеме проекта значило бы нарушить его же правило - абстракция создаётся под существующую потребность.

**Нагрузочного тестирования нет.** Это отдельный инструментарий и отдельная дисциплина. Замер async выше - разовый скрипт для документации, а не нагрузочный тест.

**Petstore не поднимается локально.** Тестируется публичный стенд как есть, со всеми его особенностями, включая чужие данные и эпизодические пятисотки. Часть найденных расхождений видна именно потому, что сервер настоящий.

**ruff и mypy не подключены.** Инструмент добавляется под конкретную задачу, а не для галочки в списке технологий.
